How I Built My Personal Website with AI in One Day, and Why

19 Mar, 2026
|

Start with the Takeaways

This article is a full account of how I built and deployed my personal website alex-huang.dev in a single day — starting from nothing. No idea, no design, no template.

The toolchain: ChatGPT → Google Gemini → Claude Code → GitHub Pages.

Total time: about 7–8 hours. No design files, no purchased template. The only cost was a $12 domain.

Three conclusions worth remembering:

  1. AI tools don’t make decisions for you — they help you turn vague ideas into actionable specs, fast
  2. Gemini handles prototyping; Claude Code handles the deep work. They’re different stages in the same pipeline, not competing tools
  3. Deployment is the most underestimated part — leave yourself enough time for it

Why I Wrote This

When I graduated from university, I built my first personal website to help with job hunting. WordPress, stock theme, weeks of on-and-off effort before it finally went live. At the time, I thought that was an achievement.

Last week, out of nowhere, I thought: now that I have more tools and experience than I did back then, how fast could I actually go if I started from scratch?

I set myself a challenge: zero to live in one day. “Zero” meant truly zero — I didn’t even have an idea for what kind of site I wanted.

This article is the full record: what I ran into, how I solved it, which tools actually delivered, and where I hit some gotchas.

The End Result

The finished site: alex-huang.dev

  • Home page: Hero section + skills showcase + endorsements
  • Projects page: Full case studies for 5 Salesforce / AI projects
  • Blog: A sustainably updatable technical writing section
  • Resume page: Auto-rendered from a resume data file
  • Deployment: GitHub Pages + GitHub Actions (push to publish)
  • Domain: Custom domain, HTTPS fully configured

Compared to my old WordPress version: far more maintainable, faster, essentially free to run — and more importantly, it’s a system I actually own, rather than a platform I’m just renting space on.

Environment / Prerequisites / What You’ll Need

Accounts:

  • GitHub account (for deployment, free)
  • OpenAI account (ChatGPT, for requirements gathering)
  • Google AI Studio account (Gemini, generous free tier)
  • Claude Code CLI (terminal tool, requires a Claude Pro subscription)

Local environment:

  • Node.js (v18+)
  • Git
  • A terminal (macOS Terminal / WSL / iTerm all work)

Domain:

  • Optional, but recommended. .dev domains are around $12/year, with discounts in the first year

You’ll need to be comfortable with:

  • Basic git (git add / commit / push)
  • Reading basic HTML/CSS (not writing it — just being able to recognise what you’re looking at)
  • Actually forget about it, just ask AI if you needed

The Overall Approach

The workflow breaks into four phases:

Requirements (1h)  →  Prototype (2h)  →  Deep Customisation (3–4h)  →  Deploy (1h)
    ChatGPT               Gemini              Claude Code            GitHub Pages
  • Phase 1 is the easiest to skip, but has the biggest impact: unclear requirements mean constant rework later
  • Phase 2 is the fastest, and more impressive than you’d expect: Gemini generates runnable code, not a wireframe
  • Phase 3 takes the most time, and delivers the most value: AI writes, you decide
  • Phase 4 is the most underestimated: there are a few critical steps, and any one of them can stall you

Step 1. Use ChatGPT to Turn Vague Goals into a Clear Brief

What this step achieves

Taking “I want to build a website” — and turning it into a requirements brief with a technical direction, page structure, and visual style.

Why bother

In the age of Vibe Coding, AI really can generate code from a vague prompt. But the vaguer the brief, the more rework downstream. Spending an hour getting your requirements clear saves at least four hours later.

What to do

Open ChatGPT and use it as your product consultant. Work through these prompts in order:

Tech stack:

I want to build a personal tech blog + portfolio site. Requirements:
- Static deployment, preferably GitHub Pages (free)
- Custom domain support
- Blog functionality (categories, tags, RSS)
- No backend needed

Please recommend suitable tech stacks, with pros and cons.

Design references:

Recommend 10 developer personal websites with great design, with links.
Style direction: minimal, dark mode, modern feel, medium information density.

Pick 3–5 that you genuinely like, and screenshot them for reference.

Output a requirements brief:

Based on our discussion, write a requirements brief for my personal website, including:
1. Tech stack selection and rationale
2. Page structure (which pages, what's on each)
3. Visual direction (style, colour palette, typography direction)
4. Core feature list

Format it clearly — I'm going to use this brief to generate code next.

Expected outcome

You should have a 1–2 page brief covering: tech stack, page list, visual direction, and feature checklist.

FAQ

Q: How detailed does the brief need to be? A: Not extremely. The “visual direction” part matters most — a few sentences mentioning your reference sites makes a meaningful difference to Gemini’s output quality. Everything else can be rougher.

Q: I don’t know which tech stack to pick. A: For static blogs, Astro (Markdown-friendly, mature ecosystem) or Next.js (more flexible but heavier) are the top choices. I went with Astro + the astro-paper theme as a base.

How to verify

Read your brief and confirm you can answer:

  • Which pages does the site have?
  • What’s the overall visual feel? (Reference examples are a bonus)
  • What’s the deployment target?

Step 2. Use Google Gemini to Generate the Site Prototype

What this step achieves

Feed the requirements brief to Gemini and get back site code you can run locally right away.

Why Gemini

  • A generous free-tier token quota — excellent value for a one-off project like this
  • Strong at generating complete, runnable code (not pseudocode)
  • Handles long prompts — a full brief plus resume content — without losing coherence

What to do

Open Google AI Studio, start a new conversation, and paste:

I need to build a personal tech blog + portfolio site.

[Paste your requirements brief]

My resume content is below:
[Paste your resume, or key details: name, role, skills, project list]

Please generate complete website code. Tech stack: Astro + Tailwind CSS.
Requirements:
- Can run locally right away
- Dark mode by default
- Minimal modern feel, with entrance animations
- Follow the page structure in the requirements brief

Wait a few minutes — Gemini will output the full code.

Run it locally:

# For an Astro project generated by Gemini
npm install
npm run dev
# Open http://localhost:4321

Expected outcome

You’ll see a working prototype in your browser. The structure and visual direction should be roughly right. At this point you’re probably at 60–80% done.

FAQ

Q: The code Gemini generated won’t run — what do I do? A: Start with the terminal error. Dependency version conflicts are the most common culprit. Copy the error into ChatGPT and ask for a fix.

Q: The result looks nothing like what I had in mind. A: Iterate in the same conversation: “Change the Hero section on the homepage to look like this…”. Gemini retains context well — no need to start over.

Q: Can I use Claude instead of Gemini here? A: Yes, it works well. I chose Gemini for this phase because you don’t need file system access, the web interface is sufficient, and Gemini’s free quota is more generous at this stage.

How to verify

  • npm run dev runs without errors
  • Full pages are visible in the browser — no blank screens
  • No errors in the terminal (warnings are fine to ignore for now)

Step 3. Use Claude Code for Deep Customisation

What this step achieves

Building on the Gemini prototype: integrating blog functionality, migrating content, applying personal customisations, adding animations — all the work that requires understanding the full project context.

Why switch to Claude Code

Gemini is excellent at generating from scratch. But when you need to make changes to existing code, it lacks file system context. Every change requires manually copying and pasting code back and forth, and anything more complex than a simple tweak is prone to introducing bugs.

Claude Code runs locally, reads and writes files directly, and understands the full project structure from the moment you start. It handles cross-file changes — the kind that require knowing how everything fits together — far more smoothly.

What to do

Install Claude Code:

npm install -g @anthropic-ai/claude-code
claude

First run will ask you to log in with your Claude Pro account.

Launch it from your project directory:

cd your-website-folder
claude

Then describe what you need in plain language:

Convert this site to support a blog.
Blog posts should be written in Markdown, stored under src/data/blog/.
The frontmatter format should follow Astro Content Collections.
I have these old articles — please migrate them into the correct format:
[paste old article content]
Add an entrance animation to the homepage:
When the page loads, each section should fade in from below in sequence, 100ms apart.
Use pure CSS transitions — don't pull in a new animation library.

Claude Code reads your files directly, shows you the proposed changes, and writes them once you confirm.

Expected outcome

After this step, the site should be at 90–95% completion: real content, complete functionality, and the visual style you want.

FAQ

Q: Claude Code’s changes broke the site. What do I do? A: Run npm run build, copy the error back to Claude Code: “Your changes caused this error — can you fix it?” It can usually locate and resolve the issue directly.

Q: It changed something I didn’t want it to. A: Run git diff to see exactly what changed, then tell it: “Only modify X file, don’t touch Y.” Commit after each completed feature so you have easy rollback points.

Q: I can’t read the code — how do I know what it changed? A: Ask it: “Explain what you just did.” It’ll give you a plain-English summary. No need to read the code yourself.

How to verify

After completing each feature:

npm run build    # Confirm the build passes
npm run preview  # Preview the final result locally

Tick off:

  • Blog post list displays correctly
  • Clicking into a post renders the content correctly
  • Homepage entrance animation triggers properly
  • All pages build without errors

Step 4. Deploy with GitHub Pages

What this step achieves

Push your local code to GitHub, configure automatic deployment, bind your custom domain, and get the site accessible on the public internet.

Why GitHub Pages

  • Completely free
  • Native integration with GitHub repositories — push code, auto-publish
  • Supports custom domains + HTTPS

What to do

1. Create a GitHub repository and push your code:

git init
git add .
git commit -m "feat: initial launch"
git remote add origin https://github.com/your-username/repo-name.git
git push -u origin main

2. Create a GitHub Actions workflow:

Create .github/workflows/deploy.yml in your project root:

name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

3. Enable Pages in your GitHub repository settings:

Go to your repo → Settings → Pages → Source, and select GitHub Actions (not Branch).

⚠️ This step is very easy to forget. If you skip it, the first CI run will fail immediately.

4. Bind your custom domain (optional):

Create a CNAME file in your project’s public/ directory, with just your domain as the content:

alex-huang.dev

Add DNS records at your registrar:

TypeNameValue
A@185.199.108.153
A@185.199.109.153
A@185.199.110.153
A@185.199.111.153
CNAMEwwwyour-username.github.io

Then go to your repo’s Settings → Pages → Custom domain, enter your domain, and tick Enforce HTTPS.

5. Wait for the CI run to complete:

git add .github/workflows/deploy.yml public/CNAME
git commit -m "chore: add deploy workflow and custom domain"
git push

Head to the Actions tab in your GitHub repo and watch the status. Green = deployed.

Expected outcome

  • Once the CI run completes, your site is accessible at https://your-username.github.io/repo-name
  • After binding a custom domain, DNS propagation typically takes anywhere from a few minutes to a few hours, after which your custom domain will resolve

FAQ

Q: CI fails with errors related to configure-pages? A: 99% of the time, the Pages Source hasn’t been set to “GitHub Actions”. Go to Settings → Pages and fix that, then re-trigger the CI (empty commit push, or re-run manually from the Actions tab).

Q: Custom domain is configured but shows a 404? A: Check in order: (1) Are the DNS records saved at your registrar? (2) Is the CNAME file in the public/ directory? (3) Is the Custom domain filled in under Settings → Pages? (4) Has DNS propagated? (You can check with whatsmydns.net.)

Q: git push in WSL throws a permission error? A: If your SSH key has a passphrase, WSL can’t prompt you for it in a non-interactive shell. Use HTTPS with a Personal Access Token (PAT) instead:

# Generate a PAT: GitHub → Settings → Developer settings → Personal access tokens
git remote set-url origin https://<your-PAT>@github.com/username/repo-name.git
git push
# Immediately strip the token from the remote URL after pushing
git remote set-url origin https://github.com/username/repo-name.git

How to verify

  • GitHub Actions → the relevant workflow run shows green
  • The GitHub Pages URL loads the site
  • If you’ve bound a custom domain: it resolves correctly, HTTPS certificate is valid

Gotchas I Hit

Gotcha #1: GitHub Pages Source Must Be Set Before You Push

Symptom: Pushed code, Actions tab shows a failure — the configure-pages@v5 step errors out immediately.

Cause: The configure-pages action requires the repository’s Pages Source to already be set to “GitHub Actions”. GitHub doesn’t enable this by default — you have to go into Settings → Pages and change it manually.

How I found it: The Actions error log had a line saying “Pages is not enabled”.

Fix: Before creating the workflow file, go to Settings → Pages and set the Source. Then push.

Gotcha #2: npm run preview Shows the Old Version

Symptom: Changed some code, ran npm run preview, and the result looked unchanged — thought the edits had been lost.

Cause: preview serves the contents of the dist/ directory directly — it doesn’t rebuild automatically. If the last build was from an older version, that’s what preview shows.

Fix: After making changes, always run npm run build first, then npm run preview.

# Right approach
npm run build && npm run preview

# Don't use preview to verify new changes without building first

Gotcha #3: Downloaded SVG Files Were Actually Error XML

Symptom: Image not showing on the site. Running ls -lh on the file showed only 275 bytes.

Cause: Some resource URLs (e.g., files in an S3 bucket without proper access permissions) return HTTP 200 when fetched with curl, but the body is an XML error message. The filename looks correct; the contents are not:

<Error><Code>AccessDenied</Code><Message>Access Denied</Message></Error>

Fix: After downloading, check the file size. A normal SVG icon is typically >3 KB; PNGs and JPGs are larger. If a file is only a few hundred bytes, cat it and have a look.

Gotcha #4: External CDN URLs Have Expiry Times

Symptom: A few months after launch, a logo image stopped displaying.

Cause: Some CDN URLs (e.g., LinkedIn image URLs) include expiry parameters like ?e=1774483200. Once that timestamp passes, the URL stops working.

Fix: Localise all image assets. Download them to your public/images/ directory and reference local paths. Never hardcode external CDN URLs.

Why This Approach Works

The key is tool specialisation. This workflow holds together not because any single tool is exceptional, but because each tool is doing exactly what it’s best at:

  • ChatGPT’s strength is conversational brainstorming — turning vague ideas into structured requirements
  • Gemini’s strength is long-context code generation — going from blank canvas to runnable prototype, fast
  • Claude Code’s strength is local context + file system access — handling complex, cross-file changes

Each phase’s output becomes the next phase’s input. String that pipeline together, and that’s where the speed comes from.

Where This Approach Has Limits

Well-suited for:

  • Static sites (blogs, portfolios, documentation sites)
  • Personal projects with no backend or database requirements
  • Developers who aren’t afraid of a terminal
  • Time-constrained situations where you want to validate an idea quickly

Not well-suited for:

  • Dynamic features (user authentication, comment systems, databases)
  • Completely no-code scenarios (in that case, look at Wix or Squarespace)
  • Commercial sites requiring highly customised design (the time investment grows significantly)

Things that may change:

  • AI tools are evolving fast — Gemini and Claude’s code generation capabilities are still improving
  • GitHub Actions workflow syntax occasionally has breaking changes — check the official docs when in doubt
  • Domain pricing and DNS configuration varies by registrar

Wrapping Up

Three conclusions that matter:

  1. The bottleneck in AI-assisted site building isn’t code generation — it’s your ability to make decisions quickly. The clearer the brief, the more precise the AI’s execution.
  2. Gemini for prototyping, Claude Code for depth — these aren’t competing tools, they’re two stages of the same pipeline.
  3. Deployment isn’t something you squeeze into the last ten minutes. GitHub Pages configuration, DNS propagation, HTTPS certificates — any one of these can stall you. Leave yourself enough time.

Three gotchas new developers should watch out for:

  1. Set the Pages Source in GitHub Settings before pushing code — skip this and your first CI run will definitely fail
  2. Run build before preview after making changes, or you’ll be looking at an outdated version
  3. Don’t reference external CDN URLs in your code — download assets locally

If you can only remember one thing:

Don’t wait until everything is ready before you start. An incomplete brief can still get you going. An imperfect design can still ship. A living website is worth more than a perfect plan — every time.
